## Calibration fix — started (see plan.md "Calibration fix — in progress" for full detail)
Circled back to the deferred calibration gap. Working through it as a deliberate multi-step re-verification, not a one-line retrain:
1. **UI/chatbot fixed first.** `RiskMeter.jsx` no longer shows a raw numeric % — hero is now a status-colored band label ("Low/Moderate/High risk") + proportional bar. User picked the exact mockup via preview before implementing (band-label-only, not a smaller tweak). `backend/main.py`'s `/explain-chat` system prompt no longer quotes `risk_score`; new `get_risk_band()` helper mirrors `RiskMeter`'s threshold logic, and the prompt now explicitly refuses to give an exact percentage even if a user asks directly — verified live with a direct test.
2. **`CalibratedClassifierCV` added to both training scripts, retrained.** Discussed with the user first why this isn't a one-line swap: calibration is monotonic (preserves ranking, shifts the number scale), so the old thresholds (0.4/0.6) would silently flag a very different population if reused as-is — demonstrated this concretely by evaluating the calibrated model at the *old* threshold: no-show recall dropped from 92% (raw) to 12% (calibrated, same 0.4 cutoff); readmission recall dropped to **0%** at the old 0.6 cutoff. Also flagged upfront (before writing code) that `shap.TreeExplainer` can't run on a `CalibratedClassifierCV`-wrapped model, so SHAP explanations stay on the raw base model — a deliberate, documented decision, not an oversight (calibration doesn't change *why*, only rescales the final number; the raw contribution values were never shown to users anyway).
   - Implementation: `models/*/train.py` now splits data 60% fit / 20% calibrate / 20% test (test set identical to before — reproducibility for worklist/notebook preserved). Fits the raw model on the fit slice, calibrates with `method="sigmoid"` on the calibrate slice via `CalibratedClassifierCV(FrozenEstimator(model), ...)` — checked the installed sklearn version (1.9.0) first since `cv="prefit"` has been replaced by `FrozenEstimator` in recent sklearn, didn't guess from memory. Saves `calibrated_v1.joblib` alongside the existing `gradient_boosting_v1.joblib`.
3. **Re-verified with an updated `notebooks/05_calibration_check.ipynb`** (raw vs. calibrated side-by-side plots + Brier scores for both models). Confirmed calibration worked: worst-bucket gap shrank from +0.337/+0.430 (raw) to ±0.018/±0.009 (calibrated); Brier score improved 32% (no-show), 56% (readmission).
4. **Threshold re-derivation — discussed method with the user before computing anything.** User asked directly whether recall/precision was still the right lens now that scores are calibrated — walked through why calibration doesn't invalidate that (rank-preserving), but *does* newly unlock a more principled cost-based/expected-value approach. Worked the textbook formula (`threshold = cost_of_intervention / cost_of_missed_outcome`) with illustrative cost assumptions for both models — both came out near-zero (~0.007 no-show, ~0.005 readmission), which for readmission actually **contradicted** the original "favor precision" framing, because it doesn't account for a care coordinator's outreach capacity being finite (unlike a free-to-scale SMS reminder). Surfaced that gap explicitly rather than quietly picking a number. User chose: no-show gets a deliberately capped, less-extreme threshold rather than the raw cost-math answer; readmission gets a capacity-based cutoff (top ~10% riskiest patients). Generated real threshold-sweep tables from the actual calibrated held-out scores so the user picked from real numbers, not the abstract math alone. **Landed on 0.20 / 0.20** (no-show: ~55% flagged, 83% recall; readmission: ~10.8% flagged, recall 0.251, precision 0.265) — not comparable to the old raw-scale 0.4/0.6.
5. Documented the full decision trail in `plan.md`.

## Deployment
User asked how to deploy. Researched current (2026) free-tier options before recommending anything (landscape shifts fast) — landed on Render (backend) + Netlify (frontend), both free tier.

**Blockers found and fixed first**: every frontend fetch call was hardcoded to `localhost:8000` (new `frontend/src/config.js`, `API_URL` from `VITE_API_URL` env var, all six components updated); backend CORS only allowed `localhost:5173` (now reads an `ALLOWED_ORIGINS` env var); no `requirements.txt` existed (written and verified installing cleanly in a fresh venv); `data/raw/`'s two runtime-needed CSVs were gitignored (un-ignored + committed, ~28MB, public/anonymized data, no privacy concern — `IDS_mapping.csv` left out since it's not actually read at runtime).

**First-ever commit**: the repo had a GitHub remote configured but zero commits before today. Staged everything, double-checked no secrets/generated files leaked in (`.env`, `alerts.db`, `__pycache__` all correctly absent), committed, and — after the user hit a git-push auth wall (GitHub dropped password auth for git in 2021; walked them through generating a Personal Access Token instead) — pushed successfully.

**Render (backend) setup**: walked through account creation, Web Service config (root dir `backend`, build/start commands, `GEMINI_API_KEY` secret). Deployed successfully; verified with curl that the data-dependent `/worklist/no-show` endpoint returned correct calibrated scores — confirmed models and the committed CSVs both loaded correctly on the live server. Root endpoint flickered 404/200 intermittently right after deploy (`x-render-routing: no-server` header) — diagnosed as Render's own free-tier spin-up instability, not an app bug, and it settled down.

**Netlify (frontend) setup — hit two real problems, both diagnosed from actual logs, not guessed**:
1. First deploy attempt logged `Detected 0 framework(s)` / `No build steps found` and deployed raw repo files instead of running `vite build` — the Base directory/Build command/Publish directory settings hadn't actually been applied during import. Fixed by setting them explicitly in Project configuration and triggering a fresh deploy; second attempt's log showed a real `vite build` run (32 modules transformed, `dist/` output) and the site went live correctly.
2. After that, the No-Show form threw "Load failed" in-browser even though curl to the backend worked. Diagnosed as CORS: preflight `OPTIONS` requests were returning 400 with no `access-control-allow-origin` header (confirmed via curl with an `Origin` header matching the Netlify domain) — meaning `ALLOWED_ORIGINS` hadn't propagated yet. Had the user check Render's deploy logs directly rather than guessing; after the env var's redeploy actually completed, re-tested and got a clean 200 with the correct CORS header.

**Found and fixed a real bug along the way**: the chatbot hung indefinitely (120s+, verified by literally leaving a curl request running and confirming the process was still alive minutes later) when deployed, despite working fine locally. Root cause: `genai.Client()` had no request timeout, so a network hiccup between Render and Google's API (a known class of issue on some cloud providers — flaky outbound routing that hangs instead of failing fast) blocked forever instead of erroring. Checked the `google-genai` SDK's actual `HttpOptions` fields before guessing at a fix, found `timeout` (milliseconds), added an explicit 20s timeout plus a try/except returning a clean 502 instead of an unhandled hang/crash. Verified live post-fix: chat endpoint responded correctly in 9 seconds.

**End state, confirmed by the user**: everything working — predictions, worklist, Overview, Alerts, and the chatbot all live and functioning against the deployed backend at `https://accessiq-backend-ur89.onrender.com`, frontend at `https://accessiq0814.netlify.app`.
